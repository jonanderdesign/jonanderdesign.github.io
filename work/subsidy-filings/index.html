Subsidy Filings.

How companies in Spain claim back part of their training costs: from paperwork prepared by hand to a flow inside Factorial.

Overview

Company
Factorial, HR software
Team
The engineering manager and the training team’s engineers
When
June to August 2026, live on 27 August
Result
158 filings from 22 companies in its first 11 weeks, not counting the beta companies

Screens use invented data.

The problem

Companies in Spain can recover part of what they invest in training through FUNDAE, the public foundation that manages these subsidies. To do so, they have to file three things for every course: the course itself, the start of each group and the end of each group. Each filing is an XML file that FUNDAE validates against its own schemas, and the three are spread over months.

Paperwork outside the product. Factorial already stored all the data these files require. However, the existing export only generated the last of the three, so HR teams prepared the other two by hand, outside the product, with the risk of FUNDAE rejecting them.

No visibility of the process. Since the start and the end are filed again for every group, a single course can involve many filings over time. Nothing in the product showed which of them had been done and which were still pending.

  1. The courseFiled once, when the course is set up
  2. →
  3. Each group startsFiled again for every group
  4. →
  5. Each group endsWhen the group finishes, with costs and participants. The only one the old export produced

The decisions

Decision 1: Generating a file is not the same as filing it.

Factorial has no connection to FUNDAE’s portal. HR downloads the file from the product and uploads it to the portal manually, sometimes days later. If the product marked a filing as done the moment the file was generated, it would be claiming something it cannot verify.

I kept the two steps separate. The product generates the file and tracks the process, and HR confirms the filing with Mark as communicated once the file has actually been submitted. The cost is that the status is only as reliable as HR’s own record, and the interface says so.

  1. GenerateFactorial builds the XML
  2. →
  3. DownloadHR saves the file
  4. →
  5. Upload to FUNDAEBy hand, outside Factorial, maybe another day
  6. →
  7. Mark as communicatedOnly HR can confirm it

Decision 2: Tracking per group, on a dedicated page.

The unit that matters is the group, not the course, because the start and the end are filed for each one. The FUNDAE process has its own page within each course, organised by step and with one row per group showing its status.

The first three layouts placed the process in a tab inside the course page. In all of them it read as one more tab rather than as a sequence of steps, so I gave it a page of its own.

Costs by company

Decision 3: Cost split by company, without a switch.

When a course belongs to a group of companies, each company can recover up to its own limit, calculated from its own participants. As soon as a course is filed that way, the product asks for the split and breaks the costs down by each participant’s company, with no option to skip it. This differs from Factorial’s training budgets, where splitting by company is a choice, and the inconsistency is deliberate: in budgets the split is the company’s preference, whereas for FUNDAE it is a condition of the filing, so a switch would only have let HR generate a file that FUNDAE would reject.

Result

In its first 11 weeks after launch, not counting the beta companies:

The flow replaced the previous export, which the team retired in October, and the training team has since built a salary-cost calculator on the same structure.

The design work was managed from Claude Code, with the specification, the tickets and the merged pull requests connected to it through MCP. I took FUNDAE’s official schemas, rather than the previous export or a demo, as the source of truth for what each filing must contain. The flow was built in real code on the production design system, in the team’s prototyping environment.

QA before launch was done by an agent of my own, built in June and already used on other projects. Given the feature and the team’s ticket format, it writes the test plan, tests in the browser and files the confirmed bugs as tickets.

On this project it worked on the live product with a test company and validated every generated file against the official schemas.

The first QA criterion was too loose. It let the agent read Mark as communicated as a claim made by the product and rank as critical several things that were not. I tightened it to the three things the product can actually get wrong: losing data, writing incorrect data into a file or stating something false. Everything else went to a separate list of design issues.

Two of the confirmed bugs were blocking: a group-start file that FUNDAE would have rejected and a group-end file that could not be generated. Both arose with groups of companies, a case that previous testing had not covered, and both were fixed before launch.
